# OctoBuddy 评审速览（v0.3.0）

**它是什么**：OctoSense 的原生 coding 应用。外环把一句话请求拆成切片，几个内环（Claude Code、Codex、pi、octos 任选）并行实现，OctoBuddy 自己跑检查、提交、发布；做出来的 OctoSense 应用上线后，它还会自己巡检、出事交给外环修。

**一句话的设计原则**：agent 只负责提议和干活；算不算完成，由 OctoBuddy 自己运行、自己读回的结果决定。

## 30 秒流程

1. 别的应用的 agent 调 `octobuddy.request`（请求按资料隔离，不当指令）→ 应用页出现请求卡片。
2. 用户点「开始做」（之前什么都不做、不花 token；只做卡片上显示的那条）。
3. 外环写任务卡，内环并行实现；OctoBuddy 跑检查、提交（回执读回），把内环的汇报对照事实标 ✓ / ✗ / ?。
4. 外环验收；检查没过或声明被驳时，OctoBuddy 拒绝 accept，除非外环写明理由给用户看。
5. 用户点发布（按钮写明要发布的内容；内容变了就拒绝）→ 发布后读回 catalog，四项核对。
6. 一轮落定后生成**验收单**：每个切片的检查、声明核对、回执、外环审阅，以及「仍需你确认的事」；用户点「确认验收」记成回执（项目变了就重新生成）。
7. Live 页每 5 分钟巡检；坏版本演练（或一条用户反馈经 `octobuddy.report` 进来）→ 事故 → 外环修 → 发布修复版 → 修复版运行正常才结案。
8. 提交 App Hub 后跟进 issue：审核人的新留言变成绑定原项目的修复请求，等用户点「开始做」，修完再提交新版本。

全程每个环都标明「工作中 / 在等谁 / 无动静 / 已结束」以及从何时起；无动静的环变警示色并提醒一次。

## 新增机制对应评分维度

| 评分维度 | v0.3.0 做了什么 |
| --- | --- |
| 需求与任务价值 | agent 完成的是「代码通过宿主检查、应用发布并读回核对、上线事故被修复、审核意见被处理后重新提交」这类可以核对的事 |
| 核心流程可用性 | 授权（开始做、发布、提交都要人确认，且绑定所见内容）→ 执行 → 核验（声明核对、提交 / 发布 / 提交审核读回）在代码里端到端可追：`src/claims.rs`、`src/receipts.rs` |
| 数据来源与失败状态 | 第三方文字（含审核留言）一律 `<untrusted>`；agent / 供应商 / gh 失败按类说明还能用什么；拒绝授权有说明；实时与过期状态分清（无动静、巡检 stale）；失败矩阵 F1–F19 见验证记录 |
| 人机协作（决赛） | 开始做、发布、提交、验收都要人确认且绑定所见内容；验收单列出「仍需你确认的事」；插话、打断并发送、接管终端随时可用 |
| 复现与材料 | 证据文件写明提交；真实与 stub 合成分开标注；单列「尚未验证」 |

## 怎么跑

- 下载 Releases 里的 DMG（Apple 芯片 / Intel 各一个，附 `.sha256`）；或 `cargo run`。
- 在 OctoSense 里：用 PR #344 的分支构建，`MAKEPAD_WM_TEST_APP=octobuddy` 直接打开 OctoBuddy。
- 测试：`cargo test --locked`（不联网、不需要 API key）。

## 诚实声明

- 声明核对与验收闸的端到端测试，内环是 stub（不调用模型）；OctoBuddy 这一侧（检查、提交、解析）是真的。
- PR #344 未合入，CI 等维护者批准运行；表中结果是本地按 CI 步骤跑的。
- Intel Mac 只在 Rosetta 下打开过；Linux、Windows 未验证。
